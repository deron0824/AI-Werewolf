## 1. 变更背景

用户真实试玩（1-2 个真人在**局域网两台电脑**上游玩）后反馈 6 条问题：

| # | 类型 | 问题一句话 |
| --- | --- | --- |
| F1 | Bug (P0) | 1 真人开局时第 6 席位空缺，未自动补满 AI |
| F2 | Bug (P0) | 局域网第二台电脑无法游玩（疑似前端连接地址写死 localhost） |
| F3 | 规则呈现 (P0) | 用户质疑女巫能否自救；规则本身（不可自救）与网易标准一致**不改**，但缺规则展示入口，且需全量复核规则实现 |
| F4 | 功能 (P1) | 真人发言无时间限制，节奏慢 |
| F5 | 新功能 (P1) | AI 发言只有文字，希望像真人一样"说出来" |
| F6 | Bug (P0) | 一局结束后「同房间再开一局」失败 |

迭代 2 目标：**3 个 P0 Bug/部署问题全部修复 + 规则可信可查 + 2 个 P1 体验增强**，AI 云端 TTS 留作未来扩展点（P2）。

## 2. 增量需求池

### P0 — 必须完成（本次交付门槛）

#### I-P0-1 席位自动补满（对应 F1）

- **需求**：开始游戏时，服务端按板子总席位数（6）自动填充 AI，补齐所有非真人席位。任意真人数量（0/1/2）开局后，**席位总数恒等于配置总数**，不允许出现空位。
- **边界**：真人 2 人 → 4 AI；真人 1 人 → 5 AI；真人 0 人（未来支持时）→ 6 AI。
- **验收标准**：
  1. 仅 1 个真人点开始 → 对局内共 6 名玩家（1 真人 + 5 AI），座位区无空位；
  2. 2 真人开局 → 2 真人 + 4 AI，共 6 席（回归确认不劣化）；
  3. 补入的 AI 身份/座位/头像与其他 AI 一致，参与完整昼夜流程。

#### I-P0-2 局域网可玩（对应 F2）

- **需求**：主机启动服务后，局域网内其他设备通过 `http://<主机IP>:5173` 打开即可完整游玩（加入房间、全程对局）。前端所有连接地址（REST/Socket）必须相对化或动态推导，**禁止写死 localhost**；服务端需监听 `0.0.0.0`。若 Vite dev 模式需 HMR，WebSocket 代理也须走同源。
- **验收标准**：
  1. 主机启动后，第二台局域网电脑浏览器访问 `http://主机IP:5173`，可加入房间、看到 6 席、完整打完一局；
  2. 同机双标签页玩法回归正常；
  3. 两台机器夜间私密信息互不串屏（回归 PRD.md §5-5）；
  4. README 新增「局域网开黑指引」章节：如何查主机 IP（Windows `ipconfig`）、访问地址、**Windows 防火墙放行提示**（放行 5173/后端端口的具体操作步骤）、常见连不上排查（同网段、防火墙、IP 变动）。

#### I-P0-3 规则复核与「规则说明」入口（对应 F3）

- **需求**：
  1. **全量规则复核**（工程侧）：对照 PRD.md §2.3 逐条核对实现——夜晚顺序、狼人协同/空刀、预言家验人、女巫（不可自救 / 不可同夜双药 / 解药已用后不再告知刀口）、遗言（仅首夜死者无遗言 + 放逐者有遗言）、平票 PK 与再平票平安日、屠城胜负判定。输出复核清单（规则条目 → 代码位置 → 结论），发现不一致处一并修复。
  2. **前端「规则说明」面板**：大厅页和对局页均有入口（如 ⓘ 图标/按钮），弹窗或抽屉展示通俗中文规则：板子配置（6 人局 2狼+预言家+女巫+2平民）、夜晚睁眼顺序、女巫用药规则（**明确写"女巫全程不可自救，包括首夜"**）、遗言规则、平票 PK、屠城胜负。纯静态文案，规则不改动。
- **验收标准**：
  1. 规则复核清单覆盖 PRD.md §2.3 全部条目，无"未核对"项；
  2. 大厅和对局页均可打开规则说明，内容含上述全部要点且与 PRD 表述一致；
  3. QA 按 PRD.md §5-3 边界用例回归：同夜双药被拒、首夜自救被拒、解药用后不再告知刀口。

#### I-P0-4 修复「同房间再开一局」（对应 F6）

- **需求**：一局结束后（胜负已宣布），真人点击「同房间再开一局」可成功开新局：房间状态机完整重置（阶段/天数/死亡/票数/发言记录清零）、重新洗牌发牌、原房间成员（含断线重连 token）仍可回到新局、socket room 事件监听正确迁移或重建。
- **验收标准**：
  1. 任一结局（狼胜/好人胜/平局若存在）结束后，点击再开一局 → 新一局正常从发牌开始，全流程可跑完；
  2. 再开后旧局数据不残留（发言面板/身份牌/天数归零）；
  3. 两台真机均无需刷新页面即可进入新局；
  4. 连续再开 2 局以上不失败。

### P1 — 应该完成（本次一并交付）

#### I-P1-1 真人发言限时（对应 F4）

- **需求**：轮到真人发言时启动倒计时（默认 60 秒，服务端/配置可调，不卡太死），倒计时显示在发言输入框附近；超时自动结束该玩家发言进入下一环节（视为"过"）。AI 发言节奏不受影响。
- **验收标准**：
  1. 真人发言阶段出现 60s 倒计时且每秒刷新；
  2. 倒计时归零后发言自动结束、法官进入下一环节，游戏不卡死；
  3. 倒计时结束前手动发送发言则立即进入下一环节；
  4. 时长可通过配置修改（非硬编码 60）。

#### I-P1-2 AI 语音播报（Web Speech API）（对应 F5）

- **需求**：AI 玩家发言（含法官关键播报可选项，见待明确点）用浏览器内置 `speechSynthesis` 以语音播报，每个 AI 玩家固定绑定一组个性化参数（不同 voice + pitch/rate 组合，建议与头像/性格映射）。文字发言仍完整保留在发言面板。
- **功能点**：
  - 自动播报开关（默认建议开启，记忆用户选择）；
  - 发言面板每条 AI 发言支持点击重播；
  - zh-CN voice 优先选择；首次播放需用户手势触发（浏览器自动播放策略），实现上在首次交互后解锁；
  - 兼容 Edge/Chrome；不支持 speechSynthesis 的环境静默降级为纯文字，不影响游戏。
- **验收标准**：
  1. 4 个 AI 的语音音色可明显区分；
  2. 开关可关闭/开启自动播报；点击历史 AI 发言可重播；
  3. 断线重连后语音设置保留；
  4. 不支持 TTS 的浏览器中游戏流程不受影响。

## 3. 给架构师的待明确点

1. **前端连接地址方案**：相对路径 + 同源代理（推荐，dev/prod 通用）还是构建时注入主机地址？请定稿实现方式，原则是任何机器访问 `http://主机IP:5173` 都能直连后端。
2. **AI 语音与 LLM 生成的时序**：AI 发言流式生成时是"生成完整段后播报"还是边流边播？建议整句播报（实现简单、断句自然）。
3. **法官播报是否也配音**：建议法官关键节点（死讯/胜负）可选播报，默认关闭，避免与 AI 发言语音重叠——需要仲裁队列（同一时刻只播一条，排队播放）。请确认是否纳入本次。
4. **再开一局的实现定位**：F6 根因待工程排查（状态机未重置 / rejoin token / socket room 清理三者之一或叠加）；若涉及房间模型重构（如 room → game 的生命周期分离），请在增量设计里明确。
5. **发言倒计时的归口**：倒计时由服务端权威计时（防本地篡改/断线漂移）还是前端显示+服务端兜底？建议服务端计时 + 前端同步显示。
6. **AI 补位后的座位分配**：新补的第 5 个 AI 是补在空缺座位号还是顺延？建议补在空缺座位号，保持席位语义。
